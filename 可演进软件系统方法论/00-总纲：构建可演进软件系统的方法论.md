# 00-总纲：构建可演进软件系统的方法论

## 1. 目的

本总纲用于指导软件从脚本、单体项目到多服务系统的持续演进。

目标不是让代码“看起来复杂”或“架构看起来高级”，而是让系统在需求变化、规模增长、团队扩大、外部依赖增加时，仍能保持：

- **清晰**
- **稳定**
- **可读**
- **可扩展**
- **可测试**
- **可维护**
- **可治理**

核心目标：

> **不要把系统写成一堆完成当前需求的代码；要把系统设计成一个能够持续容纳变化的结构。**

---

## 2. 核心方法论

## 稳定内核 + 可变配置 + 可插拔扩展 + 统一契约 + 清晰边界 + 可治理演进

这是本方法论的完整表达。

```text
稳定内核
    + 可变配置
    + 可插拔扩展
    + 统一契约
    + 清晰边界
    + 可治理演进
    = 可长期维护、可持续扩展的软件系统
```

这六个部分分别解决不同问题：

| 方法论组成 | 要解决的问题            | 典型落地方式                        |
| ----- | ----------------- | ----------------------------- |
| 稳定内核  | 哪些能力应长期复用、谨慎修改？   | 领域规则、通用执行引擎、基础模型、核心协议         |
| 可变配置  | 哪些差异不值得修改代码？      | 环境参数、阈值、字段映射、开关、选择器、模型参数      |
| 可插拔扩展 | 配置不足以描述的复杂差异如何处理？ | 插件、策略、适配器、驱动、处理器              |
| 统一契约  | 不同模块和团队如何稳定协作？    | API、接口、事件 Schema、DTO、错误码、调用规范 |
| 清晰边界  | 如何避免模块互相侵入和耦合失控？  | 分层、模块化、服务边界、数据归属、依赖方向         |
| 可治理演进 | 如何避免系统升级时破坏已有能力？  | 版本管理、契约测试、灰度、监控、日志、废弃流程       |

---

## 3. 第一原则：先找不变，再处理变化

软件设计的第一步，不是选择框架或立即写代码，而是判断：

- 什么是长期稳定、多个场景都会复用的能力？
- 什么是经常变化、可以通过参数表达的差异？
- 什么是复杂特殊、必须通过代码实现的行为？
- 什么是跨模块协作时必须保持稳定的规则？

可以把任何需求拆成以下四类：

```text
需求
 ├── 稳定能力：沉淀为内核或通用组件
 ├── 参数差异：沉淀为配置
 ├── 行为差异：沉淀为插件、策略或适配器
 └── 协作规则：沉淀为统一契约
```

核心判断口诀：

> **共性进内核，参数进配置，行为进插件，协作进契约。**

---

## 4. 第二原则：新增能力优先采用“加法式扩展”

系统健康的扩展方式，应该以新增为主，而不是反复修改旧核心。

理想状态：

```text
新增一个业务场景
    ↓
新增一份配置
或新增一个插件
或新增一个独立模块
    ↓
注册或装配
    ↓
完成扩展
```

警惕以下信号：

- 每新增一个类型，都要修改同一个核心 `if-else`；
- 每新增一个客户，都复制一份完整代码；
- 每接入一个第三方，都把 SDK 调用散落在业务代码中；
- 每新增一个页面，都重新定义不一致的接口格式；
- 每个服务都各自定义错误码、分页方式和日志格式。

这些信号通常意味着：**变化没有被正确隔离。**

原则：

> **新增需求应尽量通过新增配置、新增实现、新增模块完成，而不是不断修改稳定核心。**

---

## 5. 第三原则：统一契约优先于直接依赖

任何需要协作的两个模块，都应优先通过明确的契约连接，而不是依赖对方内部细节。

契约可以是：

- 类或接口定义；
- 函数的输入与输出模型；
- REST API；
- RPC IDL；
- 消息事件格式；
- 数据 Schema；
- 错误码规范；
- 配置 Schema。

例如：

```text
前端 ←→ API 契约 ←→ 后端
服务 A ←→ RPC / 事件契约 ←→ 服务 B
业务层 ←→ Repository 接口 ←→ 数据库实现
核心系统 ←→ Gateway 接口 ←→ 第三方系统适配器
```

统一契约带来的结果是：

- 调用者不必了解实现细节；
- 实现可以被替换；
- 模块可以独立开发与测试；
- 接口可以被自动验证；
- 多人、多团队协作成本更低。

原则：

> **依赖应面向公开契约，而不是面向内部实现。**

---

## 6. 第四原则：边界比代码复用更重要

复用很重要，但错误的复用会带来更严重的耦合。

例如，两个业务场景看起来相似，但它们的业务目标、数据归属、变化节奏不同。此时强行复用同一个“大而全服务”或“万能基类”，往往会让后续修改互相影响。

判断是否应该复用时，要问：

- 它们是否共享同一个业务概念？
- 它们是否会以相同节奏变化？
- 它们是否由同一团队或同一责任边界维护？
- 它们的共同点是业务本质，还是只是代码表面相似？

原则：

> **优先复用稳定的抽象和通用能力，不要为了减少代码行数而破坏业务边界。**

---

## 7. 第五原则：核心稳定，外围可替换

系统应形成“内稳外变”的结构：

```text
内层：核心业务规则、领域模型、关键协议
中层：应用用例、流程编排、模块协作
外层：数据库、缓存、消息队列、HTTP、文件、第三方系统
最外层：环境配置、开关、渠道参数、客户差异
```

越接近内层：

- 越应稳定；
- 越应减少外部依赖；
- 越应有严格测试；
- 越应慎重修改。

越接近外层：

- 越应支持替换；
- 越应通过配置管理；
- 越应通过适配器隔离；
- 越应允许插件化扩展。

原则：

> **把最容易变化的部分放在系统边缘，把最重要、最稳定的规则留在系统中心。**

## 8. 变化归位决策树

遇到新需求、新差异或新集成时，使用以下决策方式：

```text
发现一个变化
    ↓
它是否属于多个场景反复出现的稳定能力？
    ├── 是 → 抽象为内核能力、公共模块或领域服务
    └── 否
         ↓
它是否只是参数、映射、阈值、开关或环境差异？
    ├── 是 → 放入配置层
    └── 否
         ↓
它是否属于某类渠道、客户、平台或策略的行为差异？
    ├── 是 → 定义插件、策略或适配器
    └── 否
         ↓
它是否涉及模块、服务、团队之间的协作？
    ├── 是 → 先定义并评审统一契约
    └── 否 → 在所属模块中局部实现，并保持职责边界
```

## 9. 系统演进的基本纪律

### 9.1 不让临时需求污染核心

临时需求常见表现：

- 某客户专属规则；
- 某渠道临时适配；
- 某个页面特殊展示；
- 某次数据导入导出；
- 某个环境短期参数调整。

处理方式：

- 参数差异：配置化；
- 行为差异：插件化或适配器化；
- 确实短期且不可复用：局部隔离，并记录清理条件；
- 不要直接改动核心领域规则，除非它确实改变了通用业务本质。

### 9.2 不让接口随内部实现变化

数据库表字段、缓存结构、内部类拆分、第三方 SDK 改造，都是内部实现变化。

这些变化不应无意中传递给：

- 前端；
- 外部调用方；
- 其他服务；
- 第三方合作系统。

原则：

> **内部可以重构，外部契约应尽量稳定。**

### 9.3 不让配置无限膨胀

配置不是万能的。

当配置开始拥有：

- 深层嵌套逻辑；
- 大量条件分支；
- 动态脚本；
- 难以理解的表达式；
- 只能由开发人员安全修改的复杂规则；

说明它已经接近“代码”，应考虑转换为插件、策略或领域服务。

原则：

> **配置表达参数，插件表达行为，代码表达复杂规则。**

## 10. 从脚本到平台的演进路径

这套方法论特别适合指导“脚本平台化”和“项目系统化”。

```text
阶段 1：一次性脚本
    └── 逻辑、参数、流程全部写死

阶段 2：参数化脚本
    └── 将 URL、字段、阈值、选择器等提取为配置

阶段 3：模块化工具
    └── 抽取通用执行器、数据处理器、错误处理、日志能力

阶段 4：插件化平台
    └── 不同场景通过插件、策略、适配器进行扩展

阶段 5：契约化系统
    └── 多模块、前后端、服务与第三方通过统一 API 和事件协作

阶段 6：可治理生态
    └── 具备版本、测试、灰度、观测、审计和规范化管理能力
```

演进不是为了追求复杂架构，而是为了在系统规模和变化复杂度提高时，仍然保持可控。

## 12. 总纲 Checklist

在开始设计、开发或重构前，先检查：

- [ ] 我是否已经区分了稳定能力与变化因素？
- [ ] 这项变化应该进入内核、配置、插件、契约还是局部模块？
- [ ] 是否存在把参数差异硬编码进业务逻辑的情况？
- [ ] 是否存在把复杂行为塞进配置文件的情况？
- [ ] 是否存在用不断增长的 `if-else` 承担扩展的情况？
- [ ] 模块之间是否通过稳定契约协作？
- [ ] 核心业务是否直接依赖了某个具体数据库、第三方 SDK 或基础设施？
- [ ] 是否清楚每一类数据、规则和职责归属哪个模块或服务？
- [ ] 新需求能否主要以“新增”的方式完成，而不是修改多个旧核心？
- [ ] 这次修改是否会破坏已有接口、调用方或历史数据？
- [ ] 是否需要补充测试、版本策略、日志、监控或灰度方案？

---

## 13. 最终总结

本方法论不追求一次性设计出完美架构，而是提供一种持续决策标准：

> **每次面对变化，都先判断它属于稳定能力、参数差异、行为差异还是协作规则；然后分别将其放入内核、配置、插件或契约，并通过清晰边界与治理机制控制影响范围。**

最终追求的是：

> **让系统的复杂性随着规模增长而被组织起来，而不是随着需求增加而失去秩序。**
